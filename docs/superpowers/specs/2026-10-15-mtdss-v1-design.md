# MTDSS V1 设计文档

- 日期：2026-10-15
- 状态：待评审
- 产品代号：MTDSS（Multi-Terminal Distributed Sync/Share，正式名称待定）

## 1. 概述

MTDSS 是一款商业化的跨公网设备文件互传工具：用户在自己的多台电脑上安装客户端后，设备间可以像局域网传文件一样直接互传，文件数据始终端到端加密、点对点直达，**不经任何第三方转存**。

核心卖点：轻量、便捷、快速、跨多终端、隐私（不转存第三方）。

### 1.1 目标（V1）

- 用户注册账号，在多台设备登录后，设备自动出现在彼此列表中
- 支持 Windows / Linux / macOS 三平台间的单文件、多文件、整目录传输
- 跨公网 NAT 打洞直连；同局域网自动走内网路径
- 文件数据与文件元数据（文件名、大小、清单）对信令服务器完全不可见
- 会话内断线自动重连续传

### 1.2 非目标（V1 明确不做）

- 移动端（iOS/Android）——二期
- NAT 打洞失败时的加密中继兜底——V2
- 跨会话断点续传（重启后接着传）——V2
- 好友系统 / 与他人互传——V1 只做同账号自己的设备
- 文本/剪贴板互传
- 文件持续同步（Syncthing 模式）
- 系统右键菜单 / 分享菜单集成（Windows Shell 扩展、macOS Service、Nautilus 脚本）
- mDNS 局域网发现（设备发现 V1 完全依赖信令服务器）
- 界面视觉打磨、多语言界面（国际化框架就位，V1 仅中文）
- 付费墙 / 限速

## 2. 需求共识

| 维度 | 决定 |
|---|---|
| 定位 | 商业产品，面向大众分发，AI 辅助开发为主 |
| 核心形态 | 随传随收（AirDrop 式）：选文件 → 选设备 → 发送；接收方须在线 |
| 隐私边界 | 文件数据永远 P2P 端到端加密直传；信令服务器只做账号、设备发现、打洞协调，接触不到文件明文与元数据 |
| 平台 | 首发 Windows / Linux / macOS，移动端二期 |
| 网络兜底 | V1 打洞失败即失败（明确提示），加密中继是 V2 能力 |
| 身份 | 账号体系：手机号或邮箱 + 验证码登录（无密码），设备绑定账号 |
| 关系模型 | 用户自己的多设备互传；同账号设备自动出现，无好友系统 |
| 传输范围 | 单文件、多文件批量、整个目录（含子目录、保持结构） |
| 接收体验 | 默认自动接收落盘 + 系统通知；可按设备/全局配置为需确认 |
| 界面 | V1 从简：功能可用即可，不做视觉打磨 |
| 并发 | 多传输任务并行（对不同设备发送 + 同时接收），各自独立队列 |

## 3. 总体架构

### 3.1 组件

```
┌ 设备 A ─────────────────────────────────┐
│  mtdss-ui ──IPC──▶ mtdss-daemon          │
│ (Tauri v2)    (管道/UDS)  │托盘+传输引擎   │
│                         │+信令客户端      │
└─────────────────────────┼───────────────┘
                          │ WebSocket(信令)     UDP(QUIC, 文件数据)
                          ▼                          ▼
              ┌ 信令服务器(Rust/axum) ┐      ┌ 设备 B 的 daemon ┐
              │ REST+WS+SQLite+STUN  │◀────▶│ (对端直连)        │
              └──────────────────────┘ 信令  └─────────────────┘
```

1. **`mtdss-core`（Rust 库 crate）**——无 UI 依赖的传输内核：QUIC 连接管理、NAT 打洞、分块传输、清单校验、协议状态机。产品心脏，测试重心。
2. **`mtdss-daemon`（Rust 独立进程）**——常驻核心：开机自启、拥有托盘图标（`tray-icon`）、承载 core + 信令客户端 + 账号配置 + IPC 服务端。传输与 UI 窗口完全解耦。
3. **`mtdss-ui`（Tauri v2 应用）**——纯界面：启动时自动拉起/连接已存在的 daemon；本地 IPC 走 Windows 命名管道 / Unix domain socket 上的 JSON-RPC + 事件推送，权限由操作系统限制为本用户。
4. **`mtdss-cli`（Rust 二进制）**——复用 core 的无头客户端。开发期主力测试工具（AI 辅助开发下，核心逻辑全部经 CLI 驱动测试）。
5. **信令服务器（Rust/axum + SQLite 起步）**——REST 做注册/登录/设备管理；WebSocket 做在线状态与打洞信令转发；附带自建轻量 STUN 服务（查公网映射，不接触文件数据；自建避免依赖公共 STUN 的可用性与政策）。

### 3.2 关键架构决策

- **daemon/UI 双进程从 V1 开始**：IPC 边界现在定好，避免后期翻新；UI 崩溃不影响传输；结构与 V2 移动端复用 core 的方向一致。
- **设备发现完全依赖信令服务器（V1 无 mDNS）**：服务器不可达 = 无法发现新设备，托盘明确显示离线；**已建立的 QUIC 传输不受服务器故障影响**。
- **传输路径仍优先局域网**：候选地址含本地接口地址，同网段自动直连走内网带宽。

## 4. 身份与端到端安全

### 4.1 账号层（信令服务器管辖）

- 注册/登录：手机号或邮箱 + 验证码（V1 无密码，无密码托管责任）
- 凭证：短期 JWT（访问令牌）+ 长期刷新令牌
- 服务器存储：账号、验证码消费记录、设备登记表；不存密码

### 4.2 设备层（私钥不出设备）

- 每台设备首次启动生成 **Ed25519 身份密钥对**，私钥存 OS 凭证库（Windows 凭据管理器 / macOS Keychain / Linux libsecret），永不离开设备
- 设备凭账号 JWT 向服务器登记公钥；服务器维护 `(账号, 设备ID, 公钥, 名称, 平台, 在线状态)`
- 对端从服务器取对方公钥后在本地固定（pin）

### 4.3 传输层（服务器数学上无法窥探）

- 文件数据走 QUIC（内建 TLS 1.3）：设备用身份密钥派生自签证书，连接时互验「对端证书公钥 == 服务器登记的该设备公钥」→ 信令服务器无私钥，不可能中间人
- **信令载荷端到端加密**：打洞候选地址等信令内容用双方身份密钥加密封装，服务器只转发不透明密文——文件名、大小、清单对服务器全部不可见，仅连接级元数据（何时、哪些设备 ID 间）可见
- 完整性：SHA-256 逐块校验 + 整文件哈希；manifest 由发送方身份密钥签名，接收方可验证来源

### 4.4 威胁模型（一句话版）

服务器被完全攻破的最坏后果 = 服务不可用 + 知道「某设备某时与某设备建立了连接」；文件内容、文件名、传输元数据不可见、不可篡改（证书固定 + 哈希校验拦截）。此承诺写入产品隐私声明，作为核心卖点。

## 5. NAT 打洞与连接建立

```
发起方                信令服务器              接收方
  │──连接请求(E2E密文)──▶│──转发──────────▶│
  ├─收集候选(本地IP+STUN) │      收集候选────┤
  │──候选列表(E2E密文)──▶│──转发──────────▶│
  │◀───────────候选列表───────────────────│
  ├═══ UDP 打洞(双向并发发包) ══════════════┤
  ├──── QUIC + TLS1.3(证书互验) ──────────▶│
```

1. 候选收集：本地接口地址（局域网优先）+ 自建 STUN 查公网映射
2. 打洞：双方对候选地址对并发发认证 punch 包（magic + 会话 ID + HMAC，防伪造注入），任一路径双向通即成功，在该路径上建 QUIC（quinn 单 socket 同时 client/server）
3. NAT 类型预判：STUN 两次查询判断映射行为；对称 NAT 时 UI 提前告知「直连成功率较低」
4. 超时约 8-10 秒全部失败 → V1 明确报错 + 建议（换网络/同网段）
5. 保活：QUIC keep-alive 维持 NAT 映射

## 6. 传输协议（QUIC streams 之上）

1. **清单先行**：QUIC 建立后先传 manifest——文件列表（相对路径、大小、每块 SHA-256、整文件哈希）、传输 ID、发送方签名。带版本头的 protobuf 编码，跨版本兼容。所有元数据在 QUIC 加密内。
2. **接收决策**：按目标设备本地策略自动接收或弹窗确认（文件数/总大小/来源设备）
3. **分块传输**：1 MiB 块；每文件 2-4 条 QUIC stream 并行（stream 间无队头阻塞）；写入 `.mtdss-part` 临时文件，逐块校验、坏块按需重传，整文件哈希通过后原子 rename 到目标
4. **目录重建**：按 manifest 相对路径还原；同名冲突自动改名 `name (1).ext`
5. **调度**：同时最多 K 个文件流；传输顺序先小后大（尽快出现完成项）
6. **背压**：QUIC 流控——接收端磁盘慢自动降速，无自研限速
7. **会话内断点续传**：QUIC 断开 → 指数退避重打洞重连（最多 5 次）→ 对照 manifest 只补缺失块。跨会话续传留 V2
8. **控制**：暂停（停发新块）、取消（清理 .part）；多任务并行独立队列

## 7. UI（V1 从简）

单窗口，功能可用即可：

- 设备列表（在线状态、平台标识）
- 发送入口：拖拽文件/目录 + 「发送文件」按钮
- 传输列表：进度/速度/暂停/取消
- 最小设置：登出、默认接收目录、按设备接收策略、开机自启
- 托盘：状态、接收通知、唤起主窗
- 系统通知：接收完成、传输失败
- 技术：Tauri v2 + React + TypeScript + Vite；国际化框架就位，V1 仅中文

## 8. 系统集成（V1 边界）

有：开机自启（三平台）、托盘常驻、系统通知、拖拽发送。
无（V2）：右键菜单集成、分享菜单。

## 9. 工程结构

```
mtdss/
├─ crates/
│  ├─ core/       # 协议+打洞+传输引擎（纯库，零UI依赖）
│  ├─ daemon/     # 常驻进程：core+信令客户端+托盘+IPC服务
│  ├─ ui/         # Tauri v2 应用（React+TS）
│  └─ cli/        # 无头客户端（开发期测试主力）
├─ server/
│  ├─ signaling/  # axum：REST+WebSocket+SQLite
│  └─ stun/       # 自建STUN
├─ proto/         # protobuf 定义（信令信封+manifest）
└─ docs/          # 设计文档、协议文档
```

技术栈统一 Rust：quinn（QUIC）、tokio、axum、rusqlite、Tauri v2、tray-icon。

## 10. 错误处理

| 场景 | 行为 |
|---|---|
| 信令服务器不可达 | 托盘「离线」；已建立 P2P 传输不受影响；新发现/新连接不可用 |
| 对方离线 | 设备列表置灰；发送报「设备不在线」 |
| 打洞失败 | 明确报错 + NAT 类型提示 + 建议 |
| 传输中断 | 指数退避重连 5 次续传；超限标失败，可手动重试 |
| 磁盘不足 | 接收前预检空间 |
| 版本不匹配 | manifest 协议版本协商，不兼容提示升级 |
| 诊断 | 结构化本地日志 +「导出诊断包」（自动脱敏） |

## 11. 测试策略（AI 辅助开发的护栏）

1. 单元：core 协议状态机、分块校验、调度
2. 集成：cli↔cli 本机/容器对传，GitHub Actions CI
3. **NAT 矩阵（重心）**：Linux netns + iptables 模拟 full-cone / restricted / port-restricted / symmetric，CI 验证打洞成功/预期失败
4. 混沌：netem 丢包/延迟/断网，验证续传
5. 安全负测试：伪造 punch 包、错误证书、篡改块必须被拒
6. UI 冒烟即可，核心逻辑经 CLI 覆盖

## 12. 交付里程碑

- **M1 骨架贯通**：账号/设备登记 + 两台 cli 经信令完成局域网直连 + 单文件传输
- **M2 传输成熟**：NAT 矩阵打洞 + 分块/断点/目录传输 + 混沌测试通过
- **M3 产品成形**：daemon + 托盘 + UI 单窗口（设备/发送/进度/设置）
- **M4 可分发**：三平台安装包 + 代码签名 + 自动更新（Tauri updater）+ 开机自启 → 内测
- **M5 打磨**：错误态/通知 → 公测

成本项：Windows EV 代码签名（约 $300-500/年）、macOS Developer ID + 公证（$99/年）、更新服务托管（GitHub Releases 起步）。
