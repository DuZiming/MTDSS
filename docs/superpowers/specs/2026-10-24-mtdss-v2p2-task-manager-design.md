# MTDSS v2-P2 设计:传输任务管理

- 日期:2026-10-24

- 子项目定位:v2 总序 P0 账号+收尾 → P1 中继(已收官,main@73c5d8c)→ **P2 本设计** → P3 Android → P4 Windows UI 打磨 → P5 iOS

## 1. 意图与为什么

v2 原序列中 P2 名为「跨会话续传」。本轮 brainstorm 收窄裁定:**不做对端在线自动重发**;跨会话续传以「任务记录持久化 + 用户手动重新发起」形态交付,项目名随之改为「传输任务管理」。

解决的问题是**传输作业的生命周期绑在 daemon 进程上**:

- 作业注册表(`daemon/jobs.rs`)全在内存,daemon 一重启任务全不可见;磁盘上只有 session/settings/peers 三个 json。
- 接收端 `.mtdss/`(part+bitmap)虽留在盘上(M2c 交付的对账地基:手动重发即自动跳过/续传/新传),但桌面 UI 没有任何续传入口——用户必须记得原始路径重新发起。
- 移动端(P3/P5)断连是常态(iOS 杀后台),任务可见性 + 续传入口对移动端基本是必备地基,这也是 P2 排在 P3 前面的原因。

## 2. 目标 / 非目标

| 目标 | 内容 |
|---|---|
| 任务记录持久化 | 三类网络作业落盘,daemon 重启后任务列表完整可见(状态、最后已知进度) |
| 「中断」态 | daemon 死时 running/paused/queued 的任务,重启后标「中断」,不自动复活 |
| 重新发起 | 对失败/中断任务一键重发;源校验按文件粒度;续传走既有对账,零新传输协议 |
| 清除 | 发起端删记录;发送/调度类型跨设备清对端残留 `.part`(在线 + 回执才算成功) |
| 传输抽屉 | 底部抽屉 UI 替代右下浮卡;六列表格;类型筛选 |
| 搭车债 | 票①跨面中继推送归属歧义、票②上传旗舰 `transfer_via_relay_full` 1MiB 摊薄(§8) |

| 非目标(明确不做) | 说明 |
|---|---|
| 对端在线自动重发 | 用户裁定砍掉;不做任何自动调度 |
| 接收端「请求重发」 | 接收方向源端主动拉续传的 ctrl 新操作,用户裁定推迟(后续客户端迭代再议) |
| 被动收件任务持久化 | 别人发给我的传输不建持久记录(「记录只在发起端」);传输期间在抽屉以「接收」行可见,会话级 |
| local_copy 持久化 | 本机复制无远端面,只留在会话内 |
| 记录自动过期/上限 | 用户裁定:不自动删除;列表长了的问题 P4 再谈 |
| 传输协议改动 | manifest/块流/对账规则零改动;改动集中在 daemon 编排层、ctrl 面、UI |

## 3. 核心裁定(brainstorm 定稿)

1. **记录只在发起端**:谁发起谁持久化。发送=upload、接收=download、调度=remote_copy 三类;被动收件与 local_copy 不入。
2. **重启后一律不自动复活**:中断任务停着等用户动作。
3. **清除 = 同步的跨设备操作**:发送/调度类型对端必须在线,对端清完残留回执后才算成功,然后删本地记录;对端离线 → 清除失败,任务留着。接收类型残留本机,本地清,不依赖对端在线。
4. **源端校验按文件粒度**(重新发起时):文件还在且没变 → 对账续传/跳过(既有);在但变了 → 对端清残留、整文件重传(既有 FULL 路径:身份不符→作废旧 `.part`,零新协议);**没了 → 从 manifest 剔除不进传输,任务结果报「源已不存在」,对端把这个文件的残留清掉**。单文件、多文件、目录统一此逻辑。
5. **已完成不开重新发起**(那是重名冲突链,不是续传);完成行无操作。
6. **记录持久化,暂不考虑删除策略**。

## 4. 任务记录模型

### 4.1 存储

- 单文件 `{MTDSS_HOME}/tasks.json`,原子写(沿 settings.json 模式:临时文件 + rename)。
- 记录字段:
  - 标识:`job_id`(<dev>:<seq> 命名空间不变)、`kind`(upload|download|remote_copy)
  - 显示:`name`(首项名)、`item_count`(展开文件数)、`from_dev`/`to_dev`(方向两端,upload 源端=本机)
  - 发起参数(重发原料):源路径列表(upload=本机路径;download=源端设备上的路径;remote_copy=from 端路径)、对端设备号、目标目录、冲突策略(skip/overwrite)、cut 标志
  - 预扫 rel 全集:发起时预扫展开的 rel 清单(供重发时 diff 出「消失的文件」;O(文件数) 线性,量级与 manifest 同阶)。download/remote_copy 经 **job_query 回填**(JobQueryResponse 增 rels 字段,源端上传驱动从 manifest 回填;操作端驱动轮询时顺手写回 store);尚未回填前为空——重发 diff 退化为源端部分预检的剔除结果,行为正确只是残留清理面窄
  - 进度:`files_done/files_total`、`bytes_done/bytes_total`(download/remote_copy 计数面恒 0 的既有口径不变)
  - 状态与终因:`state`、`error`
  - 时间戳:发起、终态
- 落盘时机:状态翻转即时落盘;进度按节流落盘(≥5s 或 FileDone)。崩溃代价 = 进度回退到上个检查点,续传由对账兜底,无数据损坏。
- 内存终态上限 100(M4a)退役:持久层即历史面。内存画像:启动整载 + 增量更新,大目录记录的 rel 清单线性增长,与 manifest 同阶,可接受。

### 4.2 状态机

```
queued → running ⇄ paused
running → done | failed | cancelled
任意非终态(daemon 死)→ [重启] → interrupted
interrupted/failed → [重新发起] → running(同一条记录翻新)
```

- 重启恢复:启动时读 tasks.json,非终态(running/paused/queued)一律标 `interrupted`;终态照旧。
- **重新发起翻新同一条记录**(列表行不变、进度连续),但底层换新 job_id——防对端 `accept_orchestration` 的外部 id 撞号(对端注册表可能还持有旧 id 的重试驱动)。
- 「中断」的进度显示最后已知值;重新发起后以对账实况刷新。

## 5. 操作语义

### 5.1 重新发起(仅 failed / interrupted)

统一机制:**upload 驱动新增「部分预检」模式**——重扫当前源,缺失的顶层输入剔除并上报,不整单拒绝(普通首发仍是整单拒绝的既有口径);download/remote_copy 的重发 = 向源端重发 orchestrate(新 job id),源端以同一模式预扫。

| 类型 | 动作 |
|---|---|
| 发送 upload | 重扫本机源 → 新 job_id + 新 manifest → 连接对端(照常 connect-with-fallback)→ 先发 ctrl `cleanup_outbox`(dropped rels)再走对账传输 |
| 接收 download | 向源端重发 orchestrate(同参数、新 job id、**携旧 rel 集**)→ 源端部分预扫 → 推流;dropped 由**源端统一清接收端残留**(与发送同一机制) |
| 调度 remote_copy | 操作端向 from 端重发 orchestrate(携旧 rel 集);dropped 由源端在推流前清 to 端残留(同一机制) |

结果口径:

- 无缺失 → 正常终态;
- **有缺失 → 终态 = failed,error = 「N 项源已不存在(已清理对端残留)」**,在的文件照常传完交付;再次重新发起会重新校验(已传部分照旧 SKIP/RESUME);
- 全缺失(展开后为空)→ 拒绝发起,报错口径同「空目录」既有规则。

dropped 清理的执行是**尽力而为**:随重发流程走 ctrl,失败不阻断传输(残留内容寻址、无害,只是占空间),留日志;后续手动「清除」可回收。

### 5.2 清除

| 记录类型 | 动作 |
|---|---|
| 接收 download | 本地清该任务 rel 集在目标目录 `.mtdss/` 的记录与 `.part` → 删记录。恒可执行,不依赖对端 |
| 发送/调度 | ctrl `cleanup_outbox {dir, rels}` 发给残留所在端 → 对端清完回执 `{cleaned}` → 删本地记录。**对端离线 → 清除失败(RPC 错误「设备离线」),任务保留** |
| 已取消 | 同发送/调度(取消中断处对端可能留有 `.part`) |
| 完成 | 无操作入口(完成行不渲染按钮;对端 done 记录是后续 SKIP 素材,不动) |

- 幂等:对端按 rel 清单精确清,不存在的 rel 静默跳过;两侧列表各自独立,不做状态同步。
- **清除 = 该任务 rel 全集统一清(含已完成文件的 done 记录)——「当作没传过」语义**:清除后同内容再发走 FULL 重传,行为可预期;不保留半套记录造成隐性 SKIP。
- 退化泄漏(文档化限制):发起端设备彻底消失,则对端孤儿 `.part` 无清理入口,永留。

### 5.3 新 ctrl 操作:`cleanup_outbox`

- 请求 `{dir, rels[]}` → 响应 `{cleaned}`;走既有 ctrl 面(connect-with-fallback,含中继兜底)。
- 对端执行:`dir/.mtdss/` 内按 sha256(rel) 定位记录,身份吻合(rel 字段一致)即删记录与对应 `.part`;`.mtdss` 段保护不变(只能清隐藏区,不碰正式文件)。
- 信任边界:同账号已认证对端,与「能向该目录发送文件」同级;恶意对端最坏可删本人另一传输的续传素材(同账号内部信任,V1 口径)。
- 复用点:`清除`(§5.2)与 `重新发起的 dropped 清理`(§5.1)共用这一个操作,两个调用方。

## 6. RPC 与协议增量

- `transfer.list`:扩展为「持久层 + live 合并」(live 权威覆盖同 id 的陈旧持久态);返回字段补 name/item_count/kind 方向端。
- 新增 `transfer.reinitiate {id}` → `{}`:仅 failed/interrupted 接受;queued 期语义同普通作业;事件照常走 `event.transfer`。
- 新增 `transfer.clear {id}` → `{}`:按 §5.2;失败以 RPC code 返回(离线 = 既有「设备离线」code)。
- `event.transfer` 契约不变(状态枚举补 interrupted)。
- **proto 增量**(只增不改号):`OrchestrateRequest.old_rels = 6`(重发编排携旧 rel 集,源端 diff dropped);`JobQueryResponse.rels = 7`(源端上传驱动回填 manifest rel 集,操作端轮询回写);`CleanupOutboxRequest/Response`(ctrl oneof 双侧 field 13,§5.3)。

## 7. UI:传输抽屉

### 7.1 结构

- **底部抽屉**,挂在主窗口底部:
  - 收起(默认):细摘要条「传输 · 进行中 N · 速率 · 中断 N · 失败 N」;
  - 展开:默认约 1/4 窗高;顶边把手可拖,范围 1/4–3/4 窗高,列表内部滚动;
  - 展开/收起与高度记住(UI 本地存储,不进 daemon settings)。
- **TransferCards(右下浮卡)退役**,由抽屉统一承载;被动收件传输期间以「接收」行出现(会话级,重启即逝);托盘与状态栏速率段不变。

### 7.2 列表(六列,表头居中)

| 列 | 内容 |
|---|---|
| 任务名 | 单文件=文件名;多文件/目录=首项名 + 「· N 项」;悬停完整清单 |
| 类型 | 定宽彩色文字徽章,三色:发送蓝 `↑ 发送` / 接收绿 `↓ 接收` / 调度橙 `⇄ 调度` |
| 方向 | 源设备 → 目标设备;源/箭头/目标三段定宽,箭头纵向对齐 |
| 状态 | 进行中/已暂停/中断/失败/完成/已取消 |
| 传输速度 | 定宽进度条 + 「进度% · 速率」;失败行显示原因(如「源已不存在」) |
| 操作 | 图标按钮左对齐,悬停提示:⏸ 暂停 · ✕ 取消 · ↻ 重新发起 · 🗑 清除 |

- 操作可用性:进行中=暂停·取消(调度仅取消,既有拒 pause 语义);已暂停=继续·取消;中断/失败=重新发起·清除;已取消=清除;完成=无。
- 筛选 chips:全部 / 发送 / 接收 / 调度。

## 8. 搭车债(P1 移交)

### 8.1 票①:跨面中继推送归属歧义(开工前置)

- 现状:`daemon/fallback.rs` 的 `wait_relay_push` 按 peer 过滤取首帧,**不看会话/平面**——同 daemon 对同对端 ctrl + 传输并发兜底时,响应方可能错绑标签。窄窗、重试自愈、无数据损坏、旗舰流不触;但 P2 的**更持久重试会放大暴露**。
- 修复:`RelayAllocate` 增 `purpose` 字段(客户端自选标识,ctrl/transport 两值),服务端在 `RelayAllocated` 回显(新字段号);`wait_relay_push` 按 (peer, purpose) 过滤。旧客户端不填 → 服务端回显空 → 响应方空值不过滤(混合版本退化为现行为,不劣化)。
- 验收:同对端双面(ctrl+传输)并发兜底组合 e2e。

### 8.2 票②:上传旗舰 1MiB 摊薄

- `relay_e2e.rs` 的 `transfer_via_relay_full` 载荷 128KiB → 1MiB,套用 P1c2 第二刀裁定(实测口径:双会话固定开销 ctrl ~25KB + 传输 ~23KB;容差不放宽,1.25×);同步修失真的「回环开销≈5%」注释。

## 9. 错误与边界

| 场景 | 行为 |
|---|---|
| 清除时对端离线 | RPC 失败「设备离线」,任务保留,可稍后重试 |
| 重新发起时对端离线 | 照普通作业口径:退避重连,耗尽标失败 |
| 源部分缺失 | 在的传完交付;终态 failed + 「N 项源已不存在(已清理对端残留)」 |
| 源全部缺失 | 拒绝发起(空集规则) |
| 源变化 | 既有 FULL 路径自动作废重传,无需感知 |
| dropped 清理 ctrl 失败 | 尽力而为,不阻断传输,留日志;后续「清除」可回收 |
| tasks.json 半写/损坏 | 原子写防半写;损坏(解析失败)→ 备份后从空开始,日志告警(与 settings 同口径) |
| 重启时恰有终态落盘竞速 | 状态翻转即时落盘,窗口内崩溃 → 回退为 interrupted,无损 |
| 对端 tasks 侧无记录 | 清理通知对端无该 rel 记录 → 幂等静默 |
